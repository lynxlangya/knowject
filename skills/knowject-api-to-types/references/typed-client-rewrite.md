# Typed client rewrite

The post-extraction phase that wires the generated types into the read-api typed client.

## Two modes

| Mode | When | Behavior |
|---|---|---|
| **Primary (rewrite)** | A file matching `<api.client.output_dir>/<module>.ts` exists **and** contains the read-api header marker. | Run `rewrite-typed-client.py` to substitute `request<unknown>` and add the type imports; show diff; write on confirmation. |
| **Fallback (emit-only)** | The client file is absent or lacks the header marker. | Skip the rewriter entirely. Write only the `<module>.types.ts` file and tell the user to wire types into their own client by hand. |

## Header marker contract

The rewriter refuses any file lacking the exact substring `Generated by knowject-read-api` in its content. This is the **only** protection against accidentally clobbering user-authored client code.

If a user has edited a read-api-generated file but preserved the header comment, the rewriter will still proceed (and the user's edits will be preserved unless they conflict with the request<unknown> rewrite targets). Showing the diff before write is the user's escape hatch.

## Endpoint matching

For each `{method, path}` in the `operations_mapping`:

1. Walk the client text line by line; find lines containing `request<unknown>`.
2. For each candidate line, peek at this line + next 2 lines as a 3-line block.
3. Require the block to contain both `method: 'METHOD'` (case-insensitive) and the path string.
4. Path matches in either OpenAPI form (`/users/{id}`) or JavaScript template form (`/users/${id}`).
5. First match wins.

Endpoints that fail to match (`not_found` status in the script's stderr summary) are reported but do not abort the rewrite — partial wiring is better than refusing the whole operation.

## Import line placement

When at least one endpoint is rewritten, the rewriter inserts the type-import line **before the first non-comment, non-empty source line**. For read-api's standard output, that's right before `import { request } from '@knowject/request';`. It only imports response types actually used in `request<X>` calls, and it skips insertion if the exact same import line already exists so repeated runs do not duplicate imports. The Skill body's diff display lets the user move it if their conventions differ.

## What is NOT rewritten in Day-1

- **Body parameter types.** Functions like `(body: unknown) =>` stay `unknown`. `<X>Request` types are emitted in `<module>.types.ts` but are not imported until v2 rewrites body signatures.
- **Query parameter types.** Same reasoning.
- **Path parameter types.** Already string-typed by read-api; no further refinement.
- **Existing imports.** The rewriter prepends a new `import type` line rather than merging with any existing import block, but it does not insert the exact same import line twice. This keeps the script regex-only while preserving repeat-run safety.

## Multi-source / multi-module

If `knowject/context.yaml` declares multiple OpenAPI sources, the Skill body runs the extractor + rewriter once per source, deriving `--module <name>` from either the source's path or asking the user. Each invocation writes one `<module>.types.ts` and rewrites at most one `<module>.ts`.
